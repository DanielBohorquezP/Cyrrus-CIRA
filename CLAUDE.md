# Project guidelines

## Performance: animations & transitions

The site must always feel instant and fluid — never sluggish or janky. Apply this on every change that touches motion, scroll listeners, or transitions:

- **Never `transition-all`.** Name the exact properties (`transition-[background-color,box-shadow,border-color]`). Animating properties that don't change wastes cycles and can trigger layout/paint on unrelated properties.
- **Keep durations short.** 150ms–200ms `ease-out` for UI chrome (headers, nav, hovers). Longer durations (300ms+) read as slow on repeated interactions like scroll-driven state changes.
- **Prefer `opacity`/`transform` over layout-affecting properties.** They're GPU-composited and don't trigger reflow.
- **Don't animate `backdrop-filter`/blur radius.** Blur is expensive to recompute per frame; toggle it as a plain class swap (instant), never as part of a timed transition.
- **Throttle scroll/resize listeners to one update per frame** via `requestAnimationFrame` (see `src/lib/use-scrolled.ts`), and always register with `{ passive: true }`. Only call `setState` when a value actually crosses a meaningful threshold, not on every pixel.
- **Reuse shared hooks** (e.g. `useScrolled`) instead of duplicating scroll logic per component, so fixes/optimizations apply everywhere at once.

- **Animate a handful of elements, not a hundred.** A CSS animation on an SVG
  child (`<circle>`, `<g>`) is not composited in Blink, so every animating
  element costs a main-thread style recalc every frame. The dot spiral used to
  animate 90 circles individually — ~190ms of blocking time on its own. Group
  them and animate a few plain `<div>` wrappers with `opacity`/`transform`
  instead (see `AnimatedNavyBackground`).

When in doubt: build it, then check it in the browser preview by actually scrolling/hovering — don't assume a transition feels fine just because the code looks reasonable.

## The prerendered HTML is hydrated, not re-rendered

Every route ships as fully-rendered static HTML (`scripts/prerender.mjs`), and
`src/main.tsx` calls `hydrateRoot` on it. React attaches to the markup that is
already there instead of discarding it and rebuilding ~1,000 elements — worth
about 800ms of Total Blocking Time on a mid-range phone. That only holds while
the static HTML matches what React renders on its **first** pass. If it stops
matching, React reports a hydration error and silently rebuilds the subtree:
nothing looks broken, the page just gets slow again.

Four rules keep it matching. All four have already cost a whole page its
hydration at least once.

**1. No adjacent text children.** `{a} · {b}`, `© {year} Cyrrus`, `text{" "}<a>`
and `&ldquo;{quote}&rdquo;` are each several text nodes to React, but the DOM
merges them into one when the page is serialised. Build one string instead:

```tsx
{`${item.role} · ${item.company}`}     // not  {item.role} · {item.company}
{`Se publica en ${post.published}`}    // not  Se publica en {post.published}
```

Put a `<Link>`/`<a>` on the same line as the text before it so the space is
literal, rather than separating them with `{" "}`.

**2. No CSS shorthands or hex colours in inline `style`.** The static HTML is
serialised out of a live DOM, so the browser rewrites `transition` into four
longhands, `background` into eight, `-webkit-text-stroke` into two, and every
`#1b6fc2` into `rgb(27, 111, 194)`. React writes the original string and the two
never match. Constant decorative styles belong in `src/index.css` as a class —
see `.navy-radial-bg`, `.hero-still-gradient`, `.cira-initial-outline`. For a
value that genuinely has to be dynamic, use longhand properties and explicit
units (`translate3d(${x}px, 0px, 0px)`, never `, 0, 0`).

**3. Anything that mounts on a timer, on idle, or from a measurement must opt
out of prerender capture.** The prerenderer waits ~600ms before serialising, so
deferred content would otherwise be baked into HTML that React's first render
doesn't produce. Check `isPrerender()` (`src/lib/prerender.ts`) — as
`AnimatedNavyBackground`, `ShaderHero`, `CookieConsent` and the reveal observer
do. For a widget that can never be hydrated at all (a WebGL canvas, anything
positioned from live measurements), wrap it in `<ClientOnly>` with a
same-sized fallback.

**4. New lazy routes go in the `PAGES` table in `src/App.tsx`.** `main.tsx`
preloads the current route's chunk before hydrating, using that table. A route
whose chunk isn't loaded suspends on first render, and a suspended boundary
can't hydrate.

Verify after any change to markup or route structure:

```bash
npm run build && node scripts/serve-dist.mjs
```

then load a few routes and confirm the console is clean — a React error #418 (or
"Hydration failed…") means one of the four rules above was broken.

## Images go through `<Img>`

`src/components/ui/img.tsx` serves a size appropriate to the slot, from WebP
derivatives generated by `npm run images` (`scripts/optimize-images.mjs`) and
committed alongside the originals. The source photos are 1600px camera exports;
served raw they were 300-500KB per page for slots a third that wide.

Use `<Img>` for any image under `public/assets`, and give it a `sizes` that
matches the slot's real rendered width — the default `100vw` makes a phone
download an image wide enough to fill the screen even when the slot is a third
of it. After adding or replacing a photo, run `npm run images` and commit both
the original and `public/assets/**/opt/*`.

A plain `<img>` is still right for a remote image the pipeline doesn't own (the
YouTube thumbnail in `youtube-facade.tsx`).


## Navy sections must use AnimatedNavyBackground

Any full-bleed section with a navy/blue background — hero, CTA, social proof, etc. — must use `AnimatedNavyBackground` (`src/components/ui/animated-navy-background.tsx`) as the section wrapper, not a plain `<section className="bg-navy">`. It renders the radial navy gradient plus the pulsing dot spiral that is now the site's default look for blue sections.

Usage:

```tsx
import { AnimatedNavyBackground } from "@/components/ui/animated-navy-background";

<AnimatedNavyBackground className="py-24 md:py-32">
  {/* section content */}
</AnimatedNavyBackground>
```

It forwards `id` and other section props, so anchor targets (e.g. `id="contacto"`) keep working. Already applied to `PageHero`, `IntelligenceLabHero`, `CiraSocialProof`, and `FinalCta` — reuse it for any new navy section instead of hardcoding `bg-navy`.
